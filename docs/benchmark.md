# 模拟压测

测试日期：2026-10-19（Australia/Melbourne）。全部步骤已完成，未修改项目代码。

## 结论

本次短时模拟测试没有显示 100 个 Web 并发会明显拖慢普通查询；逐步增加到 300 并发也完成了测试。不能据此承诺生产环境支持 300 并发。

Web 实际进入了 300 个同时执行的模拟模型调用，说明它没有受到消息 Worker 的 4 槽位上限保护。Worker 的并发限制有效，但过量消息会排队。推荐先设计所有入口的并发上限、每用户限额和有界排队，再把 AI 执行进程与 API 分开；Workflow 和 Agent 可以保留在同一个执行进程内部。

## 零费用与隔离措施

没有使用正在运行的 3000 端口服务。通过 buildApp 创建独立临时服务，监听 127.0.0.1 随机端口；没有导入启动生产依赖的 server.ts，也没有读取 .env。子进程环境经过 env -i 清空，不继承真实密钥。配置只有假值。

模型、MongoDB、Redis、鉴权和消息发送均使用内存模拟，没有实例化真实模型客户端。服务端阻止全部主动 Socket/TLS/fetch/UDP 外连，客户端仅允许本次测试的 127.0.0.1 随机端口。Guard 在启动时以 example.invalid 自检，这些尝试在建立连接前被拒绝。记录到的另外两次拦截来自 tsx 尝试连接其本地开发 IPC，不是模型或业务外部服务。没有模型、数据库或消息渠道的真实调用，没有模型费用。

## 方法与边界

使用真实 Fastify buildApp、会话路由、ConversationTurnService、上下文构造与 Utf8ByteTokenCounter、AssistantWorkflow、AssistantAgent，以及 AssistantWorker。Web reply 注入按 server.ts 的讨论路由方式编排，但跟踪用量等非关键部分简化。Worker 使用真实调度逻辑，底层队列与 Redis 操作模拟；未验证真实 MongoDB 原子性、Redis 租约故障或跨机器通信。

模型分类固定等待 50 毫秒并返回 discuss；正常回复固定模拟 1 秒，慢回复模拟 10 秒。Web 每次输出 20 个 SSE 数据块，总计约 1000 个中文字符；每个新会话预置 12 条、每条约 500 个中文字符的历史。没有测试推荐搜索、长历史摘要、媒体计算、付费上游速率限制或错误重试。

客户端与服务端是同一台 arm64 Mac 上的独立进程，Node v24.13.0。未暂停其他应用，没有 CPU/内存容器配额，因此结果会受本机其他任务影响。每 50 毫秒从独立客户端请求一次真实 /api/v1/conversations 路由；该路由的会话数据及鉴权是模拟的，不能代替生产电影查询或数据库查询延迟。模型延迟固定，不代表真实供应商分布。

Web 使用闭环负载：每个并发客户端收到整条回复后发下一条；每次使用独立会话和请求 ID。正常阶段约 8 秒，慢模型阶段约 10 秒；停止发新请求后等待在途请求完成。渐进测试每 5 毫秒启动一个客户端，总计约 1.5 秒增加到 300。该测试既不是持续到达率压测，也不是数小时稳定性测试。

RSS/Heap 是服务端进程采样峰值（20 毫秒采样）；内存模拟存储保留本阶段全部会话，实际生产 MongoDB 存储方式不同。不同阶段在同一进程中依次执行，V8/RSS 可能保留上阶段分配，不能把表中 RSS 差直接解释成单条消息内存。每阶段主动 GC 只用于减少前一阶段影响，不是生产配置建议。CPU 是阶段平均值，100% 代表一个逻辑核。事件循环监测分辨率 10 毫秒，P95 约 11 毫秒不能解释为每次阻塞 11 毫秒。

## Worker 消息积压

100 条消息同时进入不同会话，模型回复模拟 1 秒，分类额外 50 毫秒。模型峰值并发 4，完成 100/100，没有发送或应用失败。约 1 秒时：96 条等待、4 条处理中。全部完成用时 27.09 秒；领取等待 P95 为 24.31 秒，最长 25.37 秒；端到端 P95 为 25.37 秒。普通查询 P95 为 4.09 毫秒，失败 0。

这证明当前限制能够约束本次模拟任务的并发，却不会消除积压。如果持续到达速度超过处理速度，排队延迟将持续增长。

## 300 并发突发连接异常

第一轮突发测试：2400 条回复成功，1457 次客户端尝试失败；普通查询失败 3 次。第一轮客户端遇到失败立即重试，会放大突发。复测增加失败后 100 毫秒等待：2400 条回复成功，131 次连接尝试失败，普通查询失败 3 次。观察到 connect ECONNRESET 和一次 write EPIPE；没有记录到服务端业务异常。

复测逐步接入 300 并发，错误 0，但该阶段复用了已有连接。随后另起全新客户端，再以每 5 毫秒一个客户端逐步接入；完成 2779 条回复，错误 0，普通查询失败 0，实际峰值模型并发 300。

本机读取到 kern.ipc.somaxconn=128。结合错误主要出现在连接建立阶段，以及全新客户端渐进接入成功，接入突发/本机 TCP 等待队列限制是合理怀疑；尚未通过抓包或内核统计证明唯一原因。没有修改内核参数，也没有把这些连接错误计为模型处理能力的上限。

## 对架构决策的含义

1. 本次没有证据要求将 Workflow 和 Agent 分别服务化；模型异步等待本身没有导致 API 延迟随等待时间等比例增加。
2. Web 需要与消息渠道一致的容量保护，并明确满载时排队或返回繁忙；消息 Worker 需要队列长度、最老消息等待时间、超时与每用户公平性策略。
3. 独立 AI 执行进程用于隔离重启、故障和资源配额；同机器拆进程仍共享硬件与数据库，不能自动增加总处理能力。未来媒体处理应有独立资源配额。
4. 生产容量仍需在目标部署资源上测试真实数据库与 Redis；可以继续用模拟模型保证零模型费用。本次没有建立该环境，也没有测出生产容量上限。
